# Per-Player state

Ticket [39] (#96) of the Phase G roadmap #94 gives the engine **Player state**: values every Player holds, declared by the ruleset and changed only through one Event. It is the first primitive the Duel Ruleset needs (Life Points, the once-per-turn summon flag) and the engine names none of them. This ADR grows with the ticket: each step of [39] appends its section below.

**Declaration.** A ruleset has an optional top-level list `player_state: [{ id, type: int | bool, init }]`, after `card_types` and before `inputs`. Each entry is a **Player-State Schema**. `init` is a scalar of the declared type, and the Empty GameState holds it for every Player, as it holds the empty zones: no Event creates the initial values, and the Event of every later change explains it. An absent key means no Player state, and a ruleset without it (the Small, Effects and Response Rulesets) behaves exactly as before. `text` (and the unsupported `enum` types) is `UnsupportedFieldType` at `player_state[<id>].type`; an `init` of another type is `InitializerTypeMismatch` at `player_state[<id>].init`; a repeated id is `DuplicateId`. The ids are in the identifier grammar. ADR-0003's typed `LifeTotal` stays in the Toy Ruleset: Life Points are a ruleset notion.

**Reading.** `{ ref: player.<id>, player: <selector> }`, in any expression (a `where`, an `if`, a `while`). It is the one expression map with two keys, and the `player:` key is allowed only when the ref starts with `player.`. `player` is therefore a reserved id: a card type id or an action param name `player` is `ReservedId` at the path an `InvalidId` of it would have. The selector depends on where the expression stands. In an action (a param `where`, a cost, an effect) a read takes `active`, the Active Player, and `opponent`, the acting Player's opponent; in a Card Effect (a triggered `if` and `do`, an activated ability's `cost` and `do`, a continuous `while`) it takes `controller`, the owner of `self`, `opponent`, the controller's opponent, and `active`. A selector the context does not accept is `UnknownPlayerSelector`; `controller` in an action is the existing `ControllerOutsideCardEffect`; a missing `player:` key is `MissingPlayerSelector`; `opponent` in a ruleset whose `players` is not 2 is `OpponentNeedsTwoPlayers { players }`. An undeclared id is `DanglingReference` to the new `ReferenceTarget::PlayerState`, at the ref; a ref of the wrong type for its slot is the existing `ExpressionTypeMismatch`. The ref is evaluated against a context that knows the acting Player (an action), the Active Player (the GameState) and the controller (the owner of `self`), kept in the bindings of the evaluation (`BoundCards`) rather than in any global. A win condition is the one place a Player Ref takes no `player:` key (see *Win conditions*).

**Writing.** `set_state` and `add_state` take `player: <selector>` in place of `card:` in action effects, action costs, a triggered `do` and the branches of `if` and `choose_one`. Both keys or neither is `InvalidStateTarget`, at the key of the primitive. A write takes the selectors of a read plus `each`, every Player in seat order. `set_state` with a value of the wrong type is `StateValueTypeMismatch` at `…set_state.value`; `add_state` on a bool is `StateValueTypeMismatch { declared: Bool, found: Int }` at `…add_state.amount`, as the card form does. In a setup step or an automatic step, `set_state` **without `zone`** writes Player state, with `zone` it keeps its meaning (the instance state of the cards of a zone), and `add_state` is new there and writes Player state only; they take `each` and `active`. `add_state` takes an int literal for now; an `amount` that is a ref or `sub` comes in a later step of this ticket.

**The Event.** `PlayerStateChanged { player, state, value }`, folded by `GameState::apply`: an unknown Player is `UnknownPlayer`, an unknown state `UnknownPlayerState { player, state }`, a value of another type than the current one `PlayerStateTypeMismatch { player, state, expected, found }`, all before anything changes. The ruleset emits it only when the value changes (as `CardStateChanged`), and `each` emits one per Player in seat order. `add_state` uses `checked_add`: an overflow in either direction is the Rejection `PlayerStateOverflow { player, state }` in an action, and `GameCreationError::PlayerStateOverflow` in a setup step or the first Turn's start; a Rejection leaves the input GameState untouched and gives no Events. The GameState holds Player state in Player order, each Player's list in the order of the schemas, read by `player_state(player)` and `player_state_value(player, state)`. Player state is **fully public**: an Observation shows every Player's state to every Viewer and the new Event is observed in full as `ObservedEvent::PlayerStateChanged`, which the Observed GameState folds (its own fields and tests, and the Relabelling's cover, are a later step of this ticket).

**Win conditions.** A `when` is a third form: a **Player-state condition**, an expression whose refs are all Player Refs without a `player:` key, such as `when: { lte: [{ ref: player.life_points }, 0] }` with `loser: owner`. Such a ref is `PlayerRefSelector::Judged`: it reads the state of the Player the condition is being judged for, and the condition is `WinConditionWhen::PlayerState`. It holds for a Player when it is true on that Player's state in the GameState the transition produced, judged for each Player in seat order, at the moments and through the path of every win condition (after each accepted Action and Pass, after an Answer, and at the end of Game creation: `end_game_if_lost`), so the ordering rules of ADR-0014 are unchanged: one Loss per Player, the first condition in declaration order is its reason, losses are in seat order, and every Player losing in one transition is a drawn Game. `loser` stays `owner`, here the Player whose state is read; no new keyword. The Judged Player is held by the evaluation context (`BoundCards`), and a Judged ref evaluated anywhere else is a typed error. Load errors: a `player:` key on a ref inside a win condition is `PlayerSelectorInWinCondition` at the ref; a `when` that reads both a card type (a Subject) and Player state is `MixedWinConditionSubject` at `win_conditions[<id>].when`; an undeclared state is `DanglingReference` to a player state; `InvalidSubjectCount` keeps its meaning for a card-only condition (a Player-only one needs no Subject). A ref without the key outside a win condition is still `MissingPlayerSelector`.

**Why not the alternatives.** A Player-state write that reuses `CardStateChanged` or a card target would make a marker card the home of a Player fact, which the roadmap rules out ("primitives, not workarounds"). A separate `player_set`/`player_add` primitive would duplicate `set_state` and `add_state` for no gain. A creation Event per initial value would put a fixed prefix in every record and every golden trace.

**Conflicts, amended in place.** ADR-0003 (the typed Player state is not the only one: a ruleset declares its own), ADR-0004 and ADR-0007 (the format's top-level keys and the typed model gain `player_state`), ADR-0010 (the Events that change a GameState, and what the Empty GameState holds), ADR-0014 (what a win condition reads), ADR-0015 and ADR-0016 (what a ref and a write may name, the effects and costs, the expression language), each carrying an `Amended by ADR-0041` marker where it stands.

**Status**: accepted
