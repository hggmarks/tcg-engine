# Listing stays a filter through transition; the GameState shares what it does not change

**The decision.** Legal Action listing keeps running one State Transition per candidate (ADR-0018 is unchanged in meaning: legal means `transition` accepts, there is one code path and no second legality check), and the cost is cut where it was measured, in six steps that change no public signature, no Event and no Listing Order:

1. **Shared ids and shared instance state.** The ids made by `id_type!` hold an `Arc<str>` instead of a `String` (same `new`, `as_str`, derived `Debug`, equality and ordering). A Card Instance's state is an `Arc<Vec<(StateName, FieldValue)>>`; `GameState::apply` copies it (`Arc::make_mut`) only when a `CardStateChanged` Event really changes a value, after the Event has been checked. A clone of a GameState then allocates per zone and per list, not per card. This does not change ADR-0002, which never fixed the memory representation: the prior GameState stays unchanged, and `PartialEq` on it is still value equality. `Arc`, not `Rc`, so a GameState stays `Send + Sync`; there is no interior mutability and no global interner.
2. **A Card Catalog index (tried, removed).** `CardCatalog::card` went through a `BTreeMap` built with the catalog. It was not faster: 43 ns per lookup in release against 38 ns for the linear scan, and 379 ns in debug against 230 ns (generic `BTreeMap::get` is unoptimized code in a debug build), and the 1,000-seed test did not get faster with it (27.9 s without it, 28.8 s with). It is removed (commit 302a896; its test of the lookup stays).
3. **Candidates without allocation per card.** `fillings` visits only the cards of the zones a param's alternatives name (the actor's zone, or the zone of every other Player for `owner: opponent`), sorted by ascending Card Instance Id with duplicates removed, and `bind_param` borrows the bindings instead of cloning them per candidate, copying only for a card that fits or for a `where` that reads them. Every card left out fails the owner or zone check of every alternative, so the result is the same set in the same Listing Order. `transition`'s own `bind` is still the authority.
4. **Linear invariant check.** `EachInstanceInOneZone` counts cards in a list indexed by Card Instance Id in one pass, with no map. The ids are dense from 0 (the engine refuses an id out of sequence); a state where they are not would report an "ids are not dense" detail instead of the old text, which the public API cannot produce.
5. **Once per run of equal definitions in `end_game_if_lost`.** The expression Win Condition looked up the Card Definition of every card of every Player (about 122 per transition) to find the cards of its Subject. Whether a card is of the Subject depends on its Card Definition alone, and the copies of a card are numbered one after the other, so the answer for the previous card is kept while the next card's definition is equal, and the lookup, and its `CardDataMismatch` error, happen at the first card with a new definition. It is exact for every GameState, hand-built ones included: it still visits every card of the Player in id order, evaluates the expression for the same cards and returns the same Events, the same Terminal Outcome and the same error at the same card. A GameState with a Leader that already meets the condition and that no Event of the transition touches still loses on the next accepted Action, and a card whose definition the catalog does not list still rejects the Action; two tests in `combat.rs` pin both, and they passed before and after the change. **This differs from the decision as first written**, which was a precomputed list of the Card Ids of the Subject's type, tested by equality without a catalog lookup. That list cannot tell a definition that is missing from the catalog from one that is not of the Subject type, so a hand-built GameState with such a card would stop being rejected; the memo keeps that error and costs less to read.
6. **`InstanceStatesMatchType` resolves a definition once per run of equal definitions**, the same memo as step 5, instead of a Card Definition lookup and a Card Type lookup per card. It verifies and reports what it did before.

**Why these.** The profile of Seeds 0..1000 before any change (commit c280834) showed no single cause. In debug, of the listing time: the clone of the GameState 31%, candidate building 27%, `end_game_if_lost` about 21%, the drop of discarded states about 10%; and of all transition time the clone was 50% and `end_game_if_lost` 33% (76% and 12% in release); the checks added 21 s, 11.6 s of it in `EachInstanceInOneZone`. One GameState clone made 497 allocations (every Card Id, every state name and every state list per card). Linear lookups by id, in `bind_param` (18.0M calls), `CardCatalog::card` (44.9M calls, 43.0M of them from `end_game_if_lost`) and the zone scans, were each cheap per call and large in number.

The wall time of this machine drifts by up to 40% between runs: further runs of 302a896 on a slower stretch took 32.7 to 47.8 s, and the baseline took 112 s in the same session where it had taken 97 s earlier. The comparison that holds is the back-to-back one: baseline 113.2 s and 111.7 s, final 32.8 s and 29.3 s.

**Target.** The ticket suggested under 25 s in debug. It is not reached: the median of the three runs of 302a896 at low load is 29.3 s. The target is therefore set at **under one third of the baseline median (96.8 s, so under 32 s)** in debug on this machine, and it is met (27.9, 29.3, 32.8 s; the last is at the line, and the slower stretch of the machine went above it). It is recorded here and not asserted by a test, because a wall-clock assertion is nondeterministic. The release figures above are the reference for throughput.

**What remains**, from the profile after step 4 (debug, ms over Seeds 0..1000, all transition calls; it was not repeated after steps 5 and 6, which removed most of the end-of-Game scan): the clone of the GameState (5,546 ms, now cheap per call, 16 us in debug), the drop of the discarded states of the listing (2,377 ms), the effects (3,204 ms), the costs (1,351 ms), `bind` (1,928 ms), and the per-transition scan of every card by `end_game_if_lost` (20,335 ms before steps 5 and 6; it still visits every card of both Players on every transition, only without a lookup per card). Listing still runs one transition per candidate (369,207 candidates for 317,829 listed Actions, the 51,378 others being plays whose mana cost cannot be paid).

**Rejected, with the numbers.**
- *A dry run without the clone* (legality without a State Transition): after step 1 the clone is no longer the main cost (6.5 us release, 16 us debug per clone), and it needs a second execution path that can also reject (an effect can fail with State Overflow), which breaks "legal is exactly what `transition` accepts".
- *A listing that returns the transitions* (self-play reuses the chosen one): it saves at most the chosen transition, 6% of the time before the steps, and changes the seam. Both stay open if a later measurement asks.
- *A precomputed list of Subject Card Ids for step 5*: see step 5.
- *Evaluating the Win Condition only on cards a transition touched*: it changes when a Win Condition is evaluated, which is a rule question, and a hand-built GameState would behave differently.
- *The Card Type on the Card Instance*: a change of public contract.
- *Pointer-keyed interning of ids*: a hack.

**What it updates.** ADR-0018's cost sentence now points here, and ADR-0004's open item "state size (performance)" says what this decided and what stays open. ADR-0020's Throughput paragraph points here. ADR-0002 is not changed: it did not fix the memory representation, and the prior GameState stays unchanged. No older ADR conflicts.

**Status**: accepted
