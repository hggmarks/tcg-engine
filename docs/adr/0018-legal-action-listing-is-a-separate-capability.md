# Legal Action listing is a separate capability of the seam

**The capability.** Listing the Legal Actions of a GameState is an optional trait, `LegalActions: Ruleset`, with one method `legal_actions(&self, state) -> Vec<Action>`, and `Runtime<R: LegalActions>` forwards to it. It is not part of `Ruleset`, which does not change. This refines ADR-0005, which left listing out of the seam: it stays out of `Ruleset`, and a Ruleset that can list says so by implementing the trait. It is separate because some Rulesets cannot list: the Toy Ruleset's DealDamage amount has no upper limit, so its legal Actions are not finite, and it does not implement the trait (a `compile_fail` doctest on the trait pins this, next to a passing one for the Declarative Ruleset).

**What is legal.** A Legal Action is exactly an Action `transition` accepts in that GameState. Listing is therefore infallible: it returns a `Vec` and has no error type, and a candidate that fails for any reason, an internal inconsistency included, is not legal and is not listed. After the Game has ended nothing is legal, and neither is anything when the Game has no current Action Phase. There is no `player` parameter: the listing is for the GameState and each Action carries its Player. In the Declarative Ruleset only the Active Player can act, so every listed Action is theirs.

**How the Declarative Ruleset lists.** It builds candidates from the Action Definitions: for each action the current phase lists, every way to bind the params in order, with the same binding check `transition` uses (owner, zone, card type, `where`, which may read earlier params). It then keeps a candidate only if `transition` accepts it. There is no second legality check, so every listed Action is accepted by construction, and completeness holds because the candidates cover every Card Instance for every param. The cost is one State Transition (a clone of the GameState, the costs and the effects) per candidate that binds. It was measured and reduced without changing this design in ADR-0021 (shared ids and instance state, candidates from the zones a param names, no per-card lookups in the end-of-Game check); a dry run without the clone, or a listing that returns the transitions, stays left for when a measurement asks for it.

**Listing Order.** Actions come in the order the current Action Phase lists its `actions`. For one action the argument lists are in lexicographic order, param by param in param order, each by ascending Card Instance Id, whatever zone the card is in. A card that fits several alternatives of a param is one candidate. The order is a property of the ruleset and the GameState alone, so two calls, or two loads of the same ruleset, give the same list.

**Status**: accepted
